# CRITICAL_AUDIT - NIGHTHAWK REV A

Date 2026-11-07. Rule followed: nothing was changed because an earlier audit claimed an error; each claim was compared with the package-specific datasheet and the physical PCB pad nets first. "Verified" below means the named file was read or the named command was run; nothing here was powered or measured.

## 1. Headline
- The "suspected errors" for U2 TCA9555PWR are not errors in this package. In the TSSOP-24 (DB/PW) pin table of TI SCPS200E: pin 1 = INT, pins 2/3 = A1/A2, pin 21 = A0 (the A0 = pin 18 / INT = pin 22 numbering belongs to the RTW/RGE QFN). Pads 1, 2, 3, 21 in NIGHTHAWK.kicad_pcb are EXP_INT, GND, GND, GND. Address bits A2:A1:A0 = 000, so the 7-bit address is 0100000 = 0x20 (datasheet slave-address table: 0 1 0 0 A2 A1 A0). Firmware EXP_I2C_ADDR = 0x20 is correct. No hardware or address change made.
- U7 TPS3823-33DBVR is mapped correctly: pad 1 /RESET -> EN, 2 GND, 3 /MR -> RESET_BTN, 4 WDI -> WDI, 5 VDD -> 3V3 (TI SLVS165O Table 5-1). Using /MR for the reset button and /RESET for ESP32 EN is the intended topology, not a fault.
- Real defects found: the firmware did not compile (2 causes), the WDI watchdog was fed unconditionally, and disarm/open did not clear the module enables. All fixed in firmware; no PCB change was needed for them.
- Full per-pin evidence: CORRECTED_PIN_MAPPING.md (generated by Hardware/build/audit_pins.py from the actual .kicad_pcb, the schematic library symbols, Firmware/include/pins.h and the datasheet tables). Result: 12 checked ICs (U1, U2, U3-U12), 0 failing pins.
- Not verified against manufacturer documents: D1 USBLC6-2SC6, J1 TYPE-C-31-M-12, J7 DM3AT-SF-PEJM5. st.com / hirose.com could not be fetched and LCSC shows the pinouts only as images. Only symbol-vs-PCB consistency was checked for them. J7 card-detect pins (9/10) and the LCSC page entry "Card Detection: No" (unconfirmed, from a page summary) are open.

## 2. Corrections (each: issue / root cause / correction / files / validation / result)

### C1 U2 TCA9555 pin map and address - NO CHANGE
- Issue: reported A0/INT swap, GND on pins 2/3, INT on GND, wrong address.
- Root cause: the report used the QFN pin numbering. Not a defect.
- Correction: none.
- Files: none modified.
- Validation: read TI SCPS200E Section 6 table (text extracted with pypdf from ti.com/lit/ds/symlink/tca9555.pdf); pcbnew pad-net dump; schematic symbol pin dump; firmware pins.h comparison (audit_pins.py).
- Result: pins 1..24 match; firmware expander bits 0..15 = P00..P07, P10..P17 match nets; address 0x20 consistent. Pad 15 (P12) is intentionally unconnected.

### C2 U7 TPS3823 - NO CHANGE
- Validation as C1 against SLVS165O. Pin mapping matches. Timing used in INTERLOCK_TRUTH_TABLE.md: ttout 0.9/1.6/2.5 s, td 120/200/300 ms.

### C3 Firmware did not build (CMake component)
- Issue: link error `undefined reference to app_main`. Root cause: the project had src/CMakeLists.txt but ESP-IDF had no component for src/. Correction: EXTRA_COMPONENT_DIRS. Files: Firmware/CMakeLists.txt. Validation: `idf.py build`. Result: builds (see FIRMWARE_BUILD_REPORT.md).

### C4 Firmware did not build (missing include)
- Issue: 'EXP_RF1_IRQ' undeclared in cli.c. Root cause: pins.h not included. Correction: include added. Files: Firmware/src/cli.c. Validation/Result: as C3.

### C5 Watchdog fed unconditionally (FIRST FIX WAS INSUFFICIENT - superseded by C7)
- Issue: the priority-10 interlock task toggled WDI every 200 ms regardless of application health, so an application hang would not trigger the hardware watchdog. Root cause: feeding tied to the monitor task only. Correction: a priority-1 health task increments a counter; WDI is toggled only while the counter advanced within the last 1 s; otherwise ARM is driven low, state = FAULT, and arming is refused. Files: Firmware/src/interlock.c. Validation: code review plus build. Result: compiled; NOT tested on hardware. Limitation: a hang that leaves the health task running is not detected (INTERLOCK_TRUTH_TABLE.md row 12).

### C6 Disarm / interlock-open did not clear module enables; arming did not clear them first
- Issue: after OPEN or disarm, RFx_EN stayed high in the expander shadow (TCA9555 is not reset by MCU reset), so a later arm could power a module immediately. Root cause: only the ARM GPIO was cleared. Correction: enter_safe_state() clears ARM, RF1_EN and RF2_EN; request_arm clears both enables before raising ARM; expander writes protected by a mutex; interlock_init() (ARM low) now runs before expander init in app_main. Files: src/interlock.c, src/expander.c, src/main.c. Validation: review + build. Result: compiled, not run on hardware.

### C7 Watchdog health monitor was incomplete (found by independent review)
- Issue: the C5 fix fed WDI when a counter incremented by `health_task`, which only proves that `health_task` runs; a blocked CLI, SD, ADC or I2C path would not stop WDI. Root cause: liveness of a helper instead of progress of the critical work. Correction: health_task removed; critical tasks (sampler, CLI) report progress at points where real work completes, with per-task deadlines; one supervisor evaluates them and is the sole owner of WDI and ARM; a stall drops ARM and stops WDI; recovery requires disarm plus a verified-low enable read-back. Files: Firmware/include/{health_core.h,supervisor_core.h,health.h,interlock.h,expander.h}, Firmware/src/{health_core.c,supervisor_core.c,health.c,interlock.c,expander.c,cli.c,storage.c,main.c,CMakeLists.txt}, Firmware/tests/host/*. Validation: host simulation (113 checks) and `idf.py build`. Result: pass in simulation and build; not tested on hardware. Details: WATCHDOG_TASK_HEALTH_MATRIX.md, FIRMWARE_TEST_REPORT.md.

### C8 expander_write error handling
- Issue: a failed write left the shadow register changed, so the shadow could claim an enable was low when it was not; callers ignored errors. Correction: shadow restored on failure, errors returned; arming and recovery do not trust writes but require a read-back of the TCA9555 output register (new expander_read_outputs) showing both enables low. Result: covered by T4/T5 in simulation.

### Additional P1 answers
- I2C failure during arm/disarm: arm fails closed (no ARM, refused); in ARMED an error drops ARM within 90-150 ms and latches FAULT; disarm cannot complete until I2C works and enables read back low, but ARM stays low meanwhile so the hardware gate keeps the rails off.
- TCA9555 during ESP32 reset: no reset pin, outputs retained (TI SCPS200E, power-on reset only). RF*_EN can remain high across an MCU reset; safety then rests on ARM/EN hardware gating, and the boot sequence clears the bits and arming requires them read back low. A failed boot clear blocks arming.
- Back-powering: with a module rail off, SPI/I2C lines can still be driven (shared with the SD card), so current may flow through the module's input protection diodes. Firmware cannot isolate the shared bus. No PCB change made: this is a design risk that depends on the module (none fitted), not a verified defect. Recommended for REV B: series resistors or a bus switch on the module connectors.
- Does the hardware guarantee module shutdown if firmware stops executing? Partly. If WDI stops, the TPS3823 resets the MCU after 0.9-2.5 s and ARM then goes low (10 k pull-down), which cuts both rails; exposure up to ttout. Reset, loop open, enclosure open cut the rails immediately. Not covered: firmware that keeps toggling WDI while wrong (now prevented only by the software supervisor), gate or load-switch failure, back-powering through signal lines. A firmware change does not fix these hardware-level limits.
